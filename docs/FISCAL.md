# Фискальные чеки: позиции из QR без официальной интеграции

## Как это работает

QR на узбекском фискальном чеке — это ссылка на публичную страницу проверки
чека (ofd.soliq.uz). Мы используем ровно то, что доступно любому человеку с
чеком в руках:

1. **Мгновенно, офлайн** (`POST /qr/resolve`): из самих параметров QR достаём
   сумму (`s=`, тийины) и дату (`YYYYMMDDHHMM`). Ответ
   `{type:'fiscal', instant:{totalAmount, datetime}, jobId}` приходит сразу —
   экран счёта открывается с тоталом, CTA «Разделить»/«Оплатить целиком»
   активны немедленно. **Инжест никогда не блокирует флоу.**
2. **Асинхронно** (in-process джоба): сервер загружает страницу чека
   (таймаут 8с + 1 ретрай, реалистичный UA, редиректы ок) и терпимо парсит
   позиции (name/qty/price/total — по семантике таблиц и меток «Итого/Jami»,
   не по хрупким путям; дробные количества «0.500» поддержаны). Валидация:
   сумма позиций = итог чека ±1000 сум. Результат кэшируется по фискальному
   ключу (повторный скан того же чека — мгновенный ответ), UI получает
   `fiscal_ready` по Socket.IO (`GET /qr/fiscal/:jobId` — то же по запросу).
3. **Фейл/таймаут >10с** — тихое состояние в дизайне: «Не удалось получить
   позиции» + чипы «📷 Сфотографировать чек» (OCR) и «Продолжить с суммой».
   Тупика нет: сумма из QR всегда на месте; нет и её — ручной ввод суммы.
4. **Экран проверки** (обязателен для fiscal/OCR перед сплитом): редактирование
   названий/сумм, степпер количества, удаление/добавление, живой индикатор
   «сумма позиций vs итог чека» (расхождение не блокирует — сплит использует
   отредактированные позиции). OCR открывает его с баннером «распознано с фото».

## OCR-фолбэк

`POST /qr/fiscal/ocr` (5/час): фото чека → Anthropic vision (модель из
`ANTHROPIC_MODEL`, ключ `ANTHROPIC_API_KEY`) → строгий JSON с позициями,
та же валидация сумм. **Приватность: изображение не сохраняется** — уходит в
API и отбрасывается (см. комментарии в fiscal.service.ts). Результат всегда
`source:'ocr'` → UI принудительно ведёт через экран проверки.

## Защита и лимиты

- Фетчится ТОЛЬКО вайтлист хостов (`OFD_HOSTS`), SSRF-guard: DNS-резолв,
  приватные адреса отклоняются; тело ≤2МБ.
- 10 чеков/час и 5 OCR/час на пользователя.
- jobId (cuid) — capability: готовый чек по нему читается (дедуп между
  пользователями), pending/failed — только владельцем.

## Мониторинг: «страница поменялась»

- Счётчики fiscal_resolved / parse_ok / parse_failed / ocr_used;
  `GET /health` → `fiscal.parseSuccessRate24h`.
- Алерт: успех <50% на последних 20 попытках (≥5 попыток) → ОДИН пост в
  `ALERT_WEBHOOK_URL` (телеграм-бот-совместимый JSON `{text}`), троттлинг 6ч,
  с именем свежего снапшота.
- Каждый фейл сохраняет сырой HTML в `var/fiscal-snapshots/` (30 дней) —
  из него новая фикстура добавляется в `test/fixtures/` за минуты:
  `pnpm test:fiscal-parser` гоняет парсер по закоммиченным страницам.

## Локальная демка (офлайн)

```bash
pnpm dev:fiscal-fixture   # ОФД-фикстура на :3299 (/check и /fail)
pnpm dev:all              # OFD_HOSTS в .env.development уже включает localhost:3299
```
На сканере в dev-режиме есть кнопка «DEV · фискальный чек» (payload можно
переопределить через localStorage `zap:fiscal-demo-payload`, напр. /fail-URL
для пути ошибки). Демо-QR печатает и `pnpm db:seed:demo`.

## Реальность ofd.soliq.uz (важно) — исследовано на реальных чеках

Живая `ofd.soliq.uz/check?...` — **SPA на React**: HTML пустой (`<div id="root">`),
данные грузятся XHR. Мы вскрыли реальный источник (headless-chromium, перехват сети):

### Источник данных = JSON-API
```
POST https://new-ofd.soliq.uz/api/payment
body: {"terminalId": t, "paymentNo": r, "paymentDate": c, "paymentType":"CHECK", "fiscalSign": s}
```
Ответ — богатый JSON: `data.extraInfo.companyName` (продавец), `data.tin` (ИНН),
`data.paymentDate` (DD.MM.YYYY HH:MM:SS), `data.cardTotal + data.cashTotal` (тотал, сумы),
`data.paymentDetails[]` (позиции). **Ключевой нюанс**: в позиции `price` — это
СТОИМОСТЬ СТРОКИ (уже цена×кол-во), сумма всех `price` == `cardTotal`; `amount` —
количество (дробное, напр. 1.268 кг). Парсер — `FiscalService.parsePaymentJson`,
покрыт тестами на двух реальных чеках (`test/fixtures/ofd-payment-{1,2}.json`).

### Параметры QR
`t`=терминал, `r`=№ чека, `c`=дата YYYYMMDDHHMMSS, **`s`=ФИСКАЛЬНЫЙ ПРИЗНАК (подпись,
НЕ сумма!)**. Убрана вся логика «сумма из URL». Мгновенно доступна только дата;
UI после скана идёт на **экран чека в состоянии загрузки** («Получаем чек…»,
скелетоны продавца/позиций/тотала) — не на пад суммы, без тоста «распознан частично»
и без нулевого тотала. Ручной ввод суммы предлагается ТОЛЬКО после неудачи фетча.

### Два блокера продакшн-фетча (факты, без обхода)
1. **Сеть**: сервер (европейский ДЦ) НЕ имеет TCP-доступа к ofd.soliq.uz и
   new-ofd.soliq.uz — `ping` проходит (~105 мс), но порты 80/443 в таймаут
   (общий интернет у сервера работает). Солик фаерволлит диапазон ДЦ.
2. **Подпись**: клиент ОФД подписывает POST заголовком `x-signature` (HMAC, секрет
   в их фронт-бандле). Серверный вызов без легального ключа мы НЕ реализуем.

Поэтому в проде `runJob` → `fetch_blocked` (см. ниже), а не `ready`.
`FiscalService.parsePaymentJson` готов и протестирован — включится, как только
появится легальный путь фетча (решение за нами): аллоу-лист IP сервера у солика,
официальный ключ API, либо фетч со стороны клиента (браузер пользователя в UZ
достаёт СВОЙ чек). Мы фетчим строго как действие пользователя над собственным
чеком, малым объёмом, честным UA; robots.txt соблюдаем (не краулим).

### Мониторинг: fetch_blocked vs parse_failed
`/health.fiscal` теперь различает: `fetch_blocked` (ОФД недоступен — инфраструктура)
и `parse_failed` (данные пришли, но не распарсились — регресс парсера).
`parseSuccessRate24h` считается только по parse_ok/parse_failed (блок сети не портит
метрику парсера). Трипваер-алерт — по parse_failed.

### ✅ РЕШЕНИЕ: клиентский фетч (телефон в UZ не заблокирован)

Сервер заблокирован соликом, но телефон пользователя (узбекский IP) — нет.
Диагностика 26.08.2026 (доказано живым 200-ответом, воспроизведено ВНЕ браузера):

- **CORS у `new-ofd.soliq.uz/api/payment` ОТКРЫТ**: preflight отражает наш origin
  (`access-control-allow-origin: https://zapapp.uz`), разрешает `POST` и заголовки
  `content-type, x-signature, x-timestamp`. Значит фетч из нашей PWA возможен.
- **Схема подписи вскрыта наблюдением** (хук `crypto.subtle` на странице ОФД, без
  брутфорса): `x-timestamp` = unix-секунды; `x-signature` =
  `HMAC_SHA256(KEY, "{terminalId}:{paymentNo}:{timestamp}")`, где `KEY =
  "thisIsPaymentSecretKey123@#"` — ПУБЛИЧНАЯ константа из их фронт-бандла
  (клиентская обфускация, не серверный секрет). Свежая подпись, посчитанная в
  standalone Node, дала **HTTP 200 с реальными позициями** — схема воспроизводима
  из публичного JS. Мы воспроизводим клиентское поведение для СОБСТВЕННОГО чека
  пользователя (низкий объём, честный UA, robots соблюдаем).

**Архитектура** (`src/lib/fiscalClient.ts` + `POST /qr/fiscal/client-result`):
1. Скан фискального QR → PWA на устройстве считает подпись (Web Crypto HMAC),
   POST-ит `new-ofd.soliq.uz/api/payment`, парсит JSON локально (та же семантика,
   `price` = стоимость строки), валидирует сумму (±1000 / ±1 на позицию), таймаут 6с.
2. Структура уходит на бэкенд `POST /qr/fiscal/client-result` (авторизовано, с
   исходным URL для дедупа/аудита). **Сервер НЕ доверяет клиентской математике** —
   сам пересчитывает суммы и валидирует форму, затем сохраняет `FiscalReceipt`
   (`source='client_fetch'`) и продолжается штатный флоу чек→проверка→сплит.
3. Клиентский путь БЫСТРЕЕ (нет раундтрипа сервер→солик). Неудача (CORS/сеть/
   таймаут/невалидные суммы) — тихо в существующий фолбэк: фото (OCR) / ручной ввод.
4. Серверный фетч остаётся в коде (для других точек входа), но в проде отдаёт
   `fetch_blocked` — клиентский путь его опережает.

Мониторинг: `/health.fiscal.bySource` = `{client_fetch, server_fetch, ocr}` с
успехами по каждому источнику.

### Фолбэк — OCR / ручной ввод
Если клиентский фетч не сработал: «📷 Сфотографировать чек» (Anthropic vision,
нужен `ANTHROPIC_API_KEY`) или «Ввести сумму вручную». Поток НИКОГДА не блокируется.
